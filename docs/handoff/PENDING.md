Pressing DOWN from native_selection==3 (PASSWORD) is SUPPOSED to always set `s->extras=1` (db1_title_menu_frame:86-90, gated on `s->released`/edge detection) rather than let the press reach the native ROM's own ("ROM `before`-hook at the same event). **Reproduced the actual inconsistency**: running the exact same button sequence (4x `PRESS DOWN 12` with `WAIT 60` between each, from NEW GAME) sometimes correctly enters EXTRAS on schedule (`local/title-wrap2-check/f01.png`, captured 1 frame after the 4th press: EXTRAS highlighted yellow, arrows shown, PASSWORD plain) -- but the SAME sequence in a separate run (`local/title-wrap3-check/e00-extras-settled.png`, screenshot taken after the 4th DOWN+WAIT60, i.e. at the point it should already show EXTRAS) instead still shows PASSWORD highlighted; a 5th DOWN press from there shows the native row-navigation arrow-pulse animation (`e01.png`) and lands on NEW GAME (`e05.png`) -- i.e. that DOWN press fell through to the native ROM's OWN 4-row (0-3) wraparound instead of being intercepted into the host's EXTRAS overlay at all. Same input sequence, two different outcomes: this points at a genuine timing race between `db1_title_menu_before()` (driven by native PC-hook observation of the guest's own code, `games/db1_title_menu.c:21-43`) and `db1_title_menu_frame()` (driven by the host's own per-frame input polling) over who "claims" the DOWN-from-row3 edge first each frame -- almost certainly the mechanism behind the owner's wraparound glitchiness. Did NOT attempt a fix: this is delicate, frame-order-dependent state-machine code where guessing wrong could make navigation worse, not better. **Mechanism clarified further**: `games/step_adapter.c:391` calls `db1_title_menu_frame()` from the input-filter path (can REPLACE the pad mask the native CPU receives that frame, `replace`/`pad` out-params); `games/step_adapter.c:172` calls `db1_title_menu_before()` from a PC-hook fired as the native 68k executes, observing whatever masked input actually reached it. The EXTRAS->NEW GAME "wrap" doesn't set `native_selection` directly -- it works by **synthetically pulsing a real DOWN press back into the native CPU** over several frames (`s->pulse<3?s->button:0` in the `pending` branch) so the GUEST ROM's OWN native row-cycling code performs its own 3->0 (or here, "skip straight past 4 to 0") wrap internally; `s->ack`/`s->wait>120` then detect whether the ROM actually responded. This is inherently timing-sensitive against however the original ROM debounces/edge-detects its own controller reads, which is the likely source of the inconsistency -- not a simple ordering bug in this host code, but a synthetic-input-timing mismatch against undocumented original ROM behavior. Fixing this properly likely needs either hardware/an accurate reference emulator to compare the ROM's actual input-debounce timing against, or much more extensive frame-by-frame tracing of the `pending`/`pulse`/`ack` state transitions than attempted here.
